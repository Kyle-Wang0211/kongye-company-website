# Phone authentication single flight (isolated website candidate)

PhoneSignInView reads CurrentUser's busy state when building but does not synchronously guard its own asynchronous send/verify entrypoints. Two taps before a rebuild can queue a second provider request and supersede the first authentication intent. A local widget reproduction with the real CurrentUser scheduler and a pending fake provider produces two requests and cancels the first successful session. This establishes the local UI defect; it does not establish the current browser's account scope or prove the cause of a particular live authentication result.

Add one synchronous per-widget in-flight guard shared by send and verify, expose it through the existing busy presentation, and reject send/verify when CurrentUser is already signed in. Release the local guard after a failure so an explicit retry remains possible. A late provider completion after widget disposal must not update the disposed widget. Preserve the original AuthService and CurrentUser implementations, provider queue and identity semantics, request values, deployment configuration, OTP expiry and work-return navigation.

Acceptance uses real PhoneSignInView taps with a completer-backed provider and the actual CurrentUser scheduler: duplicate send/verify produces one provider call; first success is not superseded; failures allow explicit retry; disposal is safe; and successful verification in the actual nested phone route returns to the existing work route. Existing login-return tests remain applicable. No live authentication, browser actions, build, deployment or phone changes are part of this candidate.
